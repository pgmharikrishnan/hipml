# WP48: tokenizer and template fidelity for real inputs

`feat/tok2`, base `a9523ef` (`feat/tail-prefill`). Every earlier number was
measured on ASCII prompts and text-only chat. This package closes the two holes
the independent review named: the pretokenizer's Unicode tables and the
untested template branches (`tool_calls`, `preserve_thinking=false`, vision
blocks).

## Pretokenizer: exact category tables

The qwen35 splitter tests `\p{L}`, `\p{N}`, `\p{M}` and `\s`. It used
`char::is_alphabetic`/`is_numeric` and a short combining-range test. Rust's
`is_alphabetic` includes the Other_Alphabetic property (many marks) and its
Unicode version can differ from the reference binary's. `unicode_tables.rs` is
now generated from llama.cpp `d7725699` (`src/unicode-data.cpp`) with only the
four bits the splitter reads; `gen_unicode_table.py` regenerates it. Every
codepoint outside a range is the reference's "other" class, which is all the
splitter needs (in-range codepoints always have a nonzero flag, so the
`as_uint()` guard cannot differ).

### Differential result

6,789 strings, tokenized by hipml and by llama-server's `/tokenize` with
`add_special=false`:

| class | strings | before | after |
| --- | ---: | ---: | ---: |
| every assigned codepoint (chunked), CJK/kana/Hangul/Tangut blocks | 550 + 214 + 36 + … | 0 | **0** |
| emoji (all blocks, 676 flags, ZWJ, skin tones, VS15/16, tag flags) | 729 | **1** | **0** |
| every Mn/Mc/Me mark, standalone and in clusters | 2,513 | 0 | **0** |
| Arabic/Hebrew/Syriac/Thaana/NKo/Samaritan/Mandaic/adlam + bidi | 57 | 0 | **0** |
| box drawing/block elements/geometric/arrows/math/tech/legacy | 21 | 0 | **0** |
| mixed ASCII/Unicode identifiers | 308 | 0 | **0** |
| whitespace edge cases | 293 | 0 | **0** |
| random valid UTF-8 (including unassigned) | 1,999 | 0 | **0** |
| **total** | **6,789** | **1** | **0** |

The one failing class had a single member, the ZWJ + VS16 sequence:

```
text:  👩‍❤️‍👨       (U+1F469 U+200D U+2764 U+FE0F U+200D U+1F468)
llama: [9008, 239, 102, 373, 235, 158938, 29545, 373, 235, 9008, 239, 101]
old:   [9008, 239, 102, 373, 235, 209726,      373, 235, 9008, 239, 101]
```

llama splits `ZWJ + ❤ | VS16`; the old table did not know U+FE0F is `\p{M}`,
so the punctuation run swallowed it and BPE merged `❤️` into one token. With
VS16 in the mark table both engines split identically. The other 2,512 mark
strings already matched because their bytes have no cross-boundary merges, so
the split difference was invisible in ids; that is why the corpus includes
sequences, not just standalone marks.

## Template branches

`bench/tokenizer/template_diff.py` feeds identical request bodies to
`/apply-template` and `hipml chat --json-file`, then compares rendered bytes
and ids. 18/18 pass:

| branch | cases | result |
| --- | --- | --- |
| text, system trim, content text parts, multi-turn reasoning | 4 | match |
| tool schemas (ASCII and Unicode names/descriptions) | 2 | ids match |
| `tool_calls` arguments: JSON string and object, escapes (`\n`, `\t`, `"`, `\`, `\u0001`, U+2028/29), nested arrays/objects, null/bool/int/float/exponent, Unicode values | 3 | ids match |
| two calls, empty content, empty `{}` arguments | 2 | ids match |
| `preserve_thinking` false/true | 2 | ids match |
| `enable_thinking` false, `reasoning_effort` low/medium | 3 | ids match |
| image and video content blocks | 2 | both rejected |

`tojson` follows nlohmann's dump: `", "` and `": "` separators, raw UTF-8,
`\u00XX` only for C0 controls, integers without a decimal point, floats always
with one (`1.0`, `1e3` -> `1000.0`, `1e-7` -> `1e-07`). String argument values
are inserted raw; strings inside arrays/objects are escaped and quoted. Vision
blocks are a hard `Unsupported` error naming the missing vision tower, never a
`<|vision_start|>` prompt.

The renderer is shared by the CLI and `hipml serve`: the server's message
builder now goes through `chat_request`/`tool_json`, so the HTTP path gets the
same tool-call and rejection behaviour.

## Permanent gate

`crates/hipml-core/tests/tokenizer_fixture.rs` replays llama's stored ids with
no llama at test time:

- `bench/tokenizer/fixture.txt`: 266 multilingual strings spanning every class
  above;
- `bench/tokenizer/template_fixture.txt`: 16 conversations, including the
  tool-call argument/escaping and `preserve_thinking` cases.

```
HIPML_GGUF=~/models/Qwen3.8-27B-Q4_K_M.gguf \
  cargo test -p hipml-core --test tokenizer_fixture
# tokenizer fixture: 266 strings match llama
# template fixture: 16 conversations match llama
```

Without a GGUF the test prints a skip; on the GPU host it finds the model at
`C:\models\Qwen3.8-27B-Q4_K_M.gguf`.

## A real coding task

`bench/tokenizer/coding_task.py` renders a multi-turn agent request: system
prompt, a user request to fix `src/café/世界.rs`, an assistant `read_file` tool
call with JSON arguments, a tool response containing Rust code with `café`,
`世界`, `👋` and `⚠️`, and a final user ask. Both engines:

- prompt: 903 bytes, 215 ids. Template text and ids **match exactly** on both
  engines (this is the tokenizer and template gate on a realistic input).
- llama-server: `-ngl 999 -fa off -ctk/-ctv f32`; hipml: `generate --device
  --kv f32 --chunk 0 --stop-eos`, greedy.

| cap | llama ids | hipml ids | first divergence | llama top-2 | margin |
| ---: | ---: | ---: | ---: | --- | ---: |
| 96 | 96 | 96 | — (identical) | — | — |
| 256 | 182 (EOS) | 171 (EOS) | 120 | 74992 −1.085, 24163 −1.278 | **0.194 nats** |

At 96 tokens the output streams are identical. At 256 both end on EOS; the
first difference is a 0.194-nat near-tie at position 120, the same arithmetic
class as the ties in WP43, not a prompt-token difference. The prompt was 215
ids on both engines.

## Checks

- `cargo test --workspace`: all suites pass (new: 3 library tests plus the
  `chat_render`, `tool_json` and `tokenizer_fixture` integration suites).
- `cargo check --workspace --features hip`: clean on gfx1201.
- `cargo build --release -p hipml-cli --features hip`: clean.

- `hipml parity --deep`: 56 passed, 0 failed, 1 skipped.

## What is unverified

- A tool argument integer outside `i64` (e.g. `12345678901234567890`): llama
  itself prints a wrapped negative value; hipml prints it as a float. This is
  a reference-side bug we do not reproduce. `i64` and below match.
- An empty-string `arguments` field: the template treats it as "no arguments",
  but llama-server rejects the request before rendering. hipml renders it; it
  is not comparable through `/apply-template`.
- A conversation whose last message is an assistant turn with
  `add_generation_prompt=false`: llama-server trims that turn's closing
  `<|im_end|>` (continue-final-message envelope), so `/apply-template` is not
  a byte-for-byte oracle there. The template rule itself
  (`loop.index0 > last_query_index` keeps `<think>`) has a unit test in
  `tests/chat_render.rs`.
- The vision branch is a deliberate rejection, not a comparison: this model
  has no vision tower, so no reference render is meaningful.
- The tables are pinned to llama.cpp `d7725699`. A newer reference with new
  Unicode assignments would need `gen_unicode_table.py` rerun.
- Only the qwen35 pretokenizer is ported; other `tokenizer.ggml.pre` types
  still use their own splitters (the model rejects non-gpt2 BPE, and the chat
  renderer validates the template signature).
